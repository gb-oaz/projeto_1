Contexto

As ferramentas e versões do projeto estão em Stack de desenvolvimento. Este documento define como o CI usa essas ferramentas: onde roda, quando cada build dispara e quais testes, verificações e coberturas reprovam o build. A geração e o envio das imagens Docker estão em Publicação das imagens.

O código vive num monorepo e segue a Metodologia git: cada tarefa numa branch própria, integrada à principal por pull request. Para poupar tempo de execução, o CI roda só os componentes cujo diretório mudou.

Antes do push, a pessoa desenvolvedora pode rodar o CI local, em 4_CI_CD/local/: uma réplica, na própria máquina e com Docker Compose, das verificações do GitHub Actions, seguida das aplicações em contêiner e dos testes de qa contra elas. Passar no CI local é a prévia de que a mudança passa no GitHub Actions, que continua sendo o veredito do merge e o único que publica imagens.

Regras de negócio

IDRegra
RN-140O CI local nunca publica imagens: as imagens que ele gera ficam só na máquina, e a publicação continua exclusiva do GitHub Actions, com aprovação (Publicação das imagens)
RN-141O CI local é uma prévia e não substitui o GitHub Actions: o merge na branch principal continua liberado só pelo job agregador do GitHub Actions (RNF-36)
RN-142Os testes de 5_DEV/qa/ cobrem comportamentos com significado para quem usa o produto (fluxos e regras dos requisitos de funcionalidade); detalhe interno de implementação fica nos testes unitários de cada componente

CI local
IDFrenteRequisito
RNF-160CI localO CI local fica em 4_CI_CD/local/ e roda com um único comando, que só exige Docker com Docker Compose v2, git e bash na máquina; para o mobile, também o SDK .NET de global.json e o workload do MAUI, com o JDK 17 e o SDK do Android (Android) e macOS com Xcode (iOS)
RNF-161CI localO CI local repete as verificações do GitHub Actions para backend, web, Android e iOS (RNF-14 a RNF-18, RNF-22, RNF-25, RNF-26 e RNF-37), com as mesmas versões de SDK, Node.js, MongoDB e Redis do CI
RNF-162CI localCom as verificações aprovadas, o CI local sobe o backend e as aplicações web em contêineres gerados pelos mesmos Dockerfiles das imagens, confere que cada um responde 200 em /health e roda contra eles os testes de 5_DEV/qa/
RNF-163CI localPor padrão, o CI local roda só os componentes alterados em relação à branch principal, incluindo mudanças ainda não commitadas, com os filtros de RNF-34 e RNF-35 (mais a própria pasta 4_CI_CD/local/); uma opção roda todos os componentes
RNF-164CI localO CI local não altera a cópia de trabalho: o repositório entra nos contêineres só para leitura, Android e iOS compilam numa cópia temporária, e banco e cache começam vazios a cada execução
RNF-165CI localO CI local termina com o resultado de cada componente e etapa e um veredito único, que falha se algum componente falhar, como o job agregador (RNF-36)
RNF-166CI localBackend e web rodam em contêineres; Android e iOS rodam direto na máquina, fora de contêiner, o iOS sempre que o app muda (sem a restrição de custo de RNF-24); app mobile cujos pré-requisitos faltam na máquina é pulado com aviso que diz o que falta, ficando a verificação para o GitHub Actions
RNF-172CI localO qa do CI local tem três abordagens, escolhidas no comando: só o backend (testes de API de 5_DEV/qa/backend/api/ contra o contêiner do backend), só o frontend (testes de ponta a ponta de 5_DEV/qa/frontend/ contra o contêiner de cada aplicação web, com o backend no ar) e as duas em conjunto sobre os mesmos contêineres, que é o padrão

O executor macOS do GitHub Actions custa mais por minuto que o Linux: por isso o build iOS roda só em pull requests para a branch principal e no merge (RNF-24).
