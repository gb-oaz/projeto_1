Contexto

O projeto é um monorepo com backend, aplicações web e mobile (Stack de desenvolvimento). A branch principal recebe só código homologado, porque é dela que saem as imagens enviadas ao Docker Hub (Publicação das imagens).

Este documento define o caminho de uma atividade, da branch de tarefa até a principal. O que o CI roda em cada branch está em CI e qualidade.

Regras de negócio

IDRegra
RN-10A branch principal do repositório é a master
RN-05Toda atividade é desenvolvida numa branch própria, criada a partir da branch principal
RN-06A branch segue o padrão tarefa_<numero>-<descricao> no desenvolvimento de um requisito (ex.: tarefa_42-cadastro) e fix_<numero>-<descricao> na correção de um bug (ex.: fix_42-erro_cadastro), em que <numero> identifica o requisito
RN-09O padrão de nome é convenção do time: o CI não recusa pull request de branch fora dele
RN-07Código entra na branch principal somente por pull request vindo de uma branch de tarefa ou de correção
RN-08Branches de tarefa e de correção não geram nem publicam imagens Docker; isso acontece só na branch principal (Publicação das imagens RNF-31)

Requisitos não funcionais

IDFrenteRequisito
RNF-39GitA branch principal tem regra de proteção no GitHub que bloqueia push direto, push forçado e exclusão
RNF-40GitO merge na branch principal exige pull request com o job agregador do CI aprovado (CI e qualidade RNF-36)
RNF-41GitO pull request para a branch principal exige 1 aprovação de revisão, e um novo commit no pull request invalida a aprovação anterior
RNF-42GitO merge na branch principal usa squash: cada pull request vira um único commit, com merge commit e rebase desabilitados
